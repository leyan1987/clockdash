- v1.28（bbcb39c，已构建双 APK）：v1.27 到 20:30 天气仍停在 19:07，
  且「同步于」也停在同一刻 → 不是天气单点问题，是后台闹钟任务整体停摆。
  根因定位：安卓 4.x AsyncTask 是全进程单线程串行队列，某次网络请求在
  DNS/连接阶段挂住即堵死后续所有闹钟任务；而 v1.27 的自愈本身也挂在
  ACTION_CHECK 的 AsyncTask 上，所以永远不生效。修法：
  ① 全项目清除 AsyncTask（AlarmReceiver CHECK/SYNC/WX、DashboardActivity
  syncNow、SettingsActivity test 全改独立 Thread；onResume 同步也不再排队）；
  ② onReceive 记录 K_LAST_ALARM，界面 mTick 每秒心跳（内部分钟级判定），
  超过 15 分钟无闹钟或缓存超过 90 分钟未更新即「心跳接管」：接管
  /api/check 推送、补拉数据、重新 schedulePeriodic 恢复提醒链路；
  ③ Store.pushChanged + healStaleData 供闹钟与界面共用，过期自愈带
  10 分钟共享退避（断网时避免 5 分钟一次全套超时请求拖垮老设备）；
  ④ 状态栏显示「闹钟停于 HH:mm · 心跳接管」，便于现场确认。
  线上对照：20:45 服务器 amap 兰山区实况 15°C（平板停在 14°C），
  config_rev=15 / todo_rev=7；自愈全链路四接口 200 验证通过。
  待用户装 v1.28 后观察状态栏「天气 HH:mm」是否在几分钟内跳到当前时间。

- 流量担忧排查（122e988）：用户担心设备关机/离线会让服务器一直发数据耗尽流量。
  核实结论：所有连接由平板主动发起，服务器没有任何重试/补发动作，离线时
  服务器→设备 0 字节；看门狗 30s 扫描纯本地 JSON 读写、不联网；唯一外发是
  告警 Webhook（发给手机不是设备），默认未配置即 0，且状态翻转才发一次。
  顺手封死两个边角：① notice 原先随每次 check 重复下发到 24h 过期（200字
  约 186 KB/天），改 NOTICE_MAX_SEND=3，计数只在设备真来取时 +1，离线期间
  不消耗次数，不影响补发可靠性；② repeat_min 可误填 1 分钟（唯一随离线
  时长线性增长的外发路径），加 MIN_REPEAT_MIN=5 下限，0 仍可关闭。
  流量账（线上实测响应体 check 45B/todos 1608B/weather 400B/config 212B/
  holidays 2440B + 保守协议开销 700B/次）：在线约 391 KB/天 ≈ 11.5 MB/月/台，
  离线 0 B；1TB 月包占 0.0011%。测试：5 次 check 只前 3 次带 notice、
  离线 sent=0、repeat 1→5 收敛、两轮 tick Webhook 调用 0 次，全通过。
